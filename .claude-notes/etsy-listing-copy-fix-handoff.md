# Handoff: fix boilerplate listing copy in the printables admin (Rails)

**Date:** 2026-08-16 · **Status:** done in this repo (all 6 work items); the
`speakanyway-printables` counterpart is still outstanding — the two ports are
deliberately out of sync until it lands.

**One deviation from the plan below**, in work item 1 / the testing table's
"overlong topic" row: with the topic capped at 6, `communication board` survives
but `speech therapy` cannot. The arithmetic doesn't close — 3 always-on + 6

a code one — left for Brittany.

posted one, so every printable ever created had a blank topic. The field is now

## Why this matters — it already happened

Nine printables published to Etsy between Aug 11–15 2026 went live with **identical
13-tag sets and identical description openers**. Combined views across all nine: 10.

Not one tag described the product. The Hospital Stay printable had no "hospital" tag;
the Hair Salon one had nothing about haircuts. Beyond weak SEO, nine listings sharing
13 tags **cannibalize each other** — Etsy caps how many results from one shop appear
per query, so they competed with each other and with the shop's established listings
instead of reaching new buyers.

Those nine were generated by the TypeScript pipeline, but `Etsy::ListingCopy` is a
port of the same logic and produces the same output. Every defect below is live in
this repo today.

The listings themselves were hand-corrected on 2026-08-16. This fixes the generator so
it stops recurring.

## Decisions (already made — don't re-litigate)

- **Deterministic templates, not an LLM.** `listing_copy.rb:7-9` notes the TS twin is
  "templates, not an LLM" — keep it that way. Testable and reproducible beats bespoke
  here.
- **"vocabulary board" → "communication board".** Both shop data and category research
  say so: all three top-viewed listings use "communication board", none of the
  zero-view ones did.
- **Add a tag-collision guard** (work item 5). This repo has every printable in one
  database, so it can detect the overlap at authoring time — something the TS pipeline
  structurally cannot do. That's the highest-value piece here.
- **Don't touch the drafts-only invariant** (`CLAUDE.md:379-386`). Nothing in this work
  publishes anything live.

## Current state

All line numbers verified 2026-08-16.

**`app/services/etsy/listing_copy.rb`** — the shared constants that make every product
read the same:

```ruby
:19  PRODUCT_HUMAN     = "vocabulary board"
:21  ALWAYS_ON_TAGS    = ["aac", "printable", "digital download"]
:22  PRODUCT_TYPE_TAGS = ["vocabulary board"]
:26  AUDIENCE_TAGS     = ["autism support", "slp", "classroom"]
:38  TOP_UP_TAGS       = ["aac printable", "communication board", "voice output aac", ...]
:64  LEAD              = "Give every voice a way to be heard with this Printable Vocabulary Board..."
```

**`app/services/etsy/copy_rules.rb:115-132`** — `assemble_tags` fills in this order:

```ruby
add.call(always_on)     # 3
add.call(product_type)  # 1
add.call(audience)      # 3
add.call(topic)         # 0 in practice — see below
add.call(top_up)        # 11 available, ~6 fit before TAG_MAX
```

Seven generic tags are committed before `topic` is consulted, and `TAG_MAX` (13) is
hit partway through `top_up`. **Even a perfectly-mined topic could only ever add a
couple of tags, at the bottom.** This ordering is the core defect.

**`topic` is usually blank.** `listing_copy.rb:95` reads `printable.topic.presence`,
and it's set from `params[:topic].presence` at
`app/controllers/admin/board_printables_controller.rb:156` — an optional field on the
create form. When blank, `CopyRules.topic_tags` returns `[]`.

The same blank topic degrades titles: `CopyRules.distinct_topic_phrase`
(`listing_copy.rb:118`) returns nil, collapsing the `pick_fitting_title` ladder
(`:124-132`) onto its bare `"<N>-Board Set"` rung. Fixing topic fixes both.

**What's already right — don't "fix" these:**

- `CopyRules.enforce_title_rules` (`copy_rules.rb:32-38`) already collapses a second
  `&` to "and". Etsy rejects two with a 400; this repo is protected, the standalone
  CLI in the printables repo is not.
- `Etsy::Client::DEFAULT_TAXONOMY_ID = 2078` (`client.rb:32`) is correct, and the
  warning at `:26-31` about the stale 6816 is accurate — 6816 silently filed listings
  under nail-art tools.
- Copy is stored in `board_printables.listing_copy` (jsonb) and is **editable in the
  admin UI** before publish. Generated copy is a starting point, not a final answer —
  which is why work item 5 matters more than perfecting the templates.

## Work items

### 1. Reserve tag slots for topic

In `CopyRules.assemble_tags` (`copy_rules.rb:115-132`), move `topic` ahead of
`product_type`/`audience`/`top_up`, capped so the proven top-up terms still land:

```
always_on → topic (max 6) → product_type → audience → top_up
```

The cap matters. An uncapped topic pool could evict `communication board` and
`speech therapy` entirely, and those appear on the listings earning traffic today.
With `always_on` at 3 and topic at ≤6, at least 4 slots remain.

Keep the method pure and keep the existing normalize/dedup behaviour. A printable with
no usable topic must produce exactly what it produces today — that's the regression
guard.

### 2. Make `topic` carry real per-product content

`listing_copy.rb` already has `board_labels` (used by `boards_section` at `:182-191`) —
the sub-board names in tree order ("Getting Ready", "At the Sink", …). That's genuine
per-product vocabulary and it's exactly what a buyer searching for that scenario types.

When `CopyRules.topic_tags(topic)` comes back empty, fall back to mining
`board_labels`. Feed the same source into `distinct_topic_phrase` so titles improve
too.

Also make the blank-topic case visible at authoring time: the create form
(`app/views/admin/board_printables/index.html.erb`) should say that leaving Topic
blank costs the listing its topical tags. A one-line hint is enough — the fallback
means it's no longer fatal, just weaker.

### 3. Rename the product-type constant

In `app/services/etsy/listing_copy.rb`:

- `:19` — `PRODUCT_HUMAN` → `"communication board"`
- `:22` — `PRODUCT_TYPE_TAGS` → `["communication board"]`
- `:38-50` — add `"vocabulary board"` to `TOP_UP_TAGS` so the smaller search term
  isn't abandoned, below the proven performers.

Watch for a duplicate: `TOP_UP_TAGS` already contains `"communication board"` at `:40`.
Once it's the product-type tag, the top-up entry is dead weight — `assemble_tags`
dedups it, but leaving both misleads the next reader. Remove it there and comment why.

Check the title logic at `:110-113` still reads correctly after the rename: `type_words`
derives from `PRODUCT_HUMAN` and drives the `names_product` branch. A board named
"Core Communication Board" will now match, which is the desired behaviour (it avoids
"Core Communication Board AAC Communication Board Printable") — but confirm with a spec.

### 4. Vary the description lead

`LEAD` (`:64`) is a frozen constant, so the opening sentence is identical on every
product. Make it a method that works the topic or board name into the first sentence —
e.g. "…this Printable Communication Board for hospital stays from SpeakAnyWay."

This is the string Google indexes and the text buyers see above the fold, so
per-product variation matters more here than anywhere else in the description. Keep the
rest verbatim — it's the top-seller's proven copy — and fall back to today's exact
wording when there's no topic.

Note the deliberate split documented at `:57-63`: prose says "free audio companion"
while tags keep "voice output aac". Preserve that.

### 5. Tag-collision guard in the admin UI (the piece unique to this repo)

Nine listings shipped with identical tags and nobody noticed until an external review
caught it. This repo has every `BoardPrintable` in one table, so it can catch this at
authoring time.

On the printable show page (`app/views/admin/board_printables/show.html.erb`, near the
listing form), surface how much this printable's tags overlap with other printables'.
Flag it when overlap is high — 10+ of 13 shared with an existing printable means
they'll compete for the same searches.

Design notes:

- **Warn, don't block.** Some overlap is correct and unavoidable: three core-vocabulary
  products genuinely share most tags because they *are* the same product at different
  sizes. The admin needs to see it and judge, not be stopped.
- Show *which* printable it collides with and *which* tags are shared, so the fix is
  obvious. A bare "high overlap" warning isn't actionable.
- Compare against printables that have `listing_copy` present. Scope to a reasonable
  recent window if the table is large enough that a full scan drags the page.

### 6. Specs

`bundle exec rspec`. Add coverage that fails against current `main`:

- **The one that would have caught this:** two printables with different topics produce
  materially different tag sets — assert at least 5 tags differ. If it passes before
  your change, the fix isn't wired.
- Topic tags appear whenever a topic or usable `board_labels` exists, and rank above
  the top-up pool.
- The topic cap holds: an overlong topic can't evict the top-up terms.
- Regression: a printable with no topic and a single board still yields today's exact
  13 tags.
- The collision guard flags a genuine duplicate and stays quiet on a legitimately
  distinct pair.

Existing specs around `Etsy::ListingCopy` and `Etsy::CopyRules` will need updating for
the rename — expect "vocabulary board" assertions to fail, and read each one before
changing it rather than find-and-replacing.

## Testing

| Scenario | Expect |
|---|---|
| Printable with topic set | topical tags present, above top-up pool |
| Printable, topic blank, multi-board | tags mined from `board_labels` |
| Printable, topic blank, single board | today's exact 13 tags (regression) |
| Overlong topic (10+ phrases) | topic capped at 6; `communication board` + `speech therapy` survive |
| Board already named "…Communication Board" | no doubled product phrase in title |
| Two near-identical printables | collision guard warns, names the shared tags |
| Title with two `&` | still collapsed to one by `enforce_title_rules` |

Run `bundle exec rspec` and report results. Admin access-control sweep
(`spec/requests/admin/access_control_spec.rb`) must stay green if you add any
controller action — see `CLAUDE.md:316-327` on gating by inheritance, not inline checks.

## Deploy notes

No migrations, no new ENV vars, no API changes. Affects newly-generated listing copy
only — existing `board_printables.listing_copy` rows are untouched, and nothing already
on Etsy changes. Safe to ship alone.

Regenerating copy for an existing printable is an explicit admin action
(`#regenerate_listing_images`, `#regenerate`), so no backfill happens implicitly.
